AI engineering project

A knowledge system that answers from its own documents, offline.

An organization is a tree of units. Each unit keeps its own documents, answers questions about them with citations, tracks its problems, and sends a short, quality-checked report up to the unit above. Everything runs on small models on a laptop, with no internet.

1. The idea

What problem does it solve?

Today, knowledge travels up an organization as written reports. That is slow, and facts get lost on the way. This project builds the same flow in software.

Idea 1

Knowledge stays at the node

A node answers only from documents stored in its own folder. A bus project can never read the water department's files. This is hard rule H01.

Idea 2

Issues link knowledge to people

A problem (an issue) points to the documents that explain it and to the people who can solve it.

Idea 3

Reports climb one layer at a time

A node writes a summary at the detail level its parent needs. A judge scores it out of 20, and only 18 or more is sent up.

The three kinds of model

Embedding model

Turns text into a list of numbers so that texts about the same thing end up close together. It finds the right pages.

Analogy: a librarian with a map of meaning
LLM

Writes the answer from the pages it is handed, cites the file, and says "insufficient knowledge" when the answer is missing.

Analogy: a writer who may only use the desk's pages
Vision model (LVM)

Reads a picture of a page, such as a scanned meeting minute, and returns text.

Analogy: a reader looking at a photograph
Why small models are enough here: the LLM does not need to know facts. It needs to follow rules. That is what the experiments test.

4. Measuring

How do we know it works?

A metric is a rule that turns "does it work?" into a number. We define the rule first, measure a baseline second, and only then set a target with the supervisor.

Metric

A named rule, such as the share of questions answered correctly.

Baseline

The value on the simplest working version. Measured, not chosen.

Target

The lowest value that is still useful. Agreed after the baseline. Still empty.

Hard rule

Must hold on every run: pass or fail, never a percentage.

How one answer is graded

Each question lists the facts a correct answer must contain. The answer is lowercased, then checked. A | means "or", a ; means "and".

Q02: How many electric buses does the agency run? Required fact: 25

The weak spot: "load rose from 71% to 94%" contains both numbers of the right answer but means the opposite. That is why a human reads every failed answer, and why the judge probe includes such cases.

7. Lessons

What we learned

Look at the answers, not only the score

qwen3:4b scored 91%, but its "answers" began "Okay, let me tackle this question..." It is a thinking-only model whose reasoning filled the reply limit. Its numbers were meaningless, so it is excluded and must be rerun with qwen3:4b-instruct.

Grading rules have bugs too

Four rules were too strict (Q07, Q08, Q17, Q19). Fixing them moved the main metric from 0.74 to 0.91, with no change in the model. Both numbers are reported, and the fix is written down.

The planted problems are real problems

With the duplicate in the index, the model cites both copies (Q03). Asked about a contradiction, it picks one side (Q06). This is the case for the next parts of the project.

Compare "right files given" with "real retrieval"

The gap between the two runs is the cost of retrieval mistakes. Here it was a single question, and it was the duplicate.

Ties on small tests are not wins

All three embedding models found every source at k=3. On 23 questions, one question is about 4 percentage points. The test cannot tell the models apart.

Real problems on the way

Windows reserved Ollama's default port after a restart, so the server uses port 11500. The Ollama installer, once tried, left traces that broke downloads until it was removed. A test written before the real run found a crash on question Q12 before any download.

Part 3: architecture

Define bounded contexts, aggregates, entities, value objects, repositories and domain services, the unit-test structure, and storage abstractions. Deliverables: a DDD architecture document, a domain model specification, and an initial unit-test plan. The key decision: which object owns which rule (for example, does a knowledge item own "exactly one active version"?).

Part 4: document ingestion

Register DOC, DOCX and PDF files, build text extraction adapters, record knowledge metadata, define the citation model, and set first chunking rules. Deliverables: an ingestion prototype, a metadata schema, and a chunking specification. Old binary DOC files are the hardest format to read.

9. Hands-on

Run it yourself

Two PowerShell windows. Window 1 runs the server and stays open. The full runbook is docs/operator_guide.md.

Window 1: the server

& "E:\UNI\Semesterr 7\AI-Engineering\UNI-Project\scripts\start_ollama.ps1"

Window 2: set up, once per window

$env:OLLAMA_HOST = "127.0.0.1:11500"
$env:OLLAMA_MODELS = "E:\UNI\Semesterr 7\AI-Engineering\ollama-models"
$ollama = "E:\UNI\Semesterr 7\AI-Engineering\ollama\ollama.exe"
$py = "E:\UNI\Semesterr 7\AI-Engineering\.venv\bin\python.exe"
$env:OLLAMA_EXE = $ollama
cd "E:\UNI\Semesterr 7\AI-Engineering\UNI-Project"

Download a model and check

& $ollama pull qwen3:4b-instruct
& $py -m baseline_runner check

Run experiments

& $py -m baseline_runner e2 --models phi4-mini --run-id e2-again
& $py -m baseline_runner e3 --embedding qwen3-embedding-0.6b --models phi4-mini --run-id e3-again
& $py -m baseline_runner regrade --run-id e3-again

Check the project

& $py -I tools\run_checks.py
& $py -m pytest
