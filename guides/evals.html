Evaluation and judges

This is the skill that most separates a senior AI engineer from everyone else. Models change every few months; knowing whether a change helped does not. Book chapters 3 and 4.

1. What an eval is

An eval is a repeatable test of an AI system: the same inputs, a fixed way of scoring, and a saved result. It plays the role that unit tests play for ordinary code, but the result is a rate, not a pass or fail, and it is noisy.

Use the cheapest checker that works, in this order:

CheckerGood forCost and risk
1. Exact match or pattern"135", a route number, a document id in the citation, valid JSON.Free, repeatable. Too strict for free text.
2. Code on key facts"The answer contains all the key facts and none of the forbidden ones." (Your answer key already has key facts.)Free, repeatable. Needs good key facts.
3. A judge modelQuality of wording, completeness, tone, faithfulness to the context.Slow, noisy, biased. Must be checked against humans.
4. A humanThe ground truth for everything above.Expensive. Use on a sample.
Senior habit Do not reach for a judge model first. Many questions with a factual answer can be scored by code. Judges are for what code cannot check, and every judge needs its own evaluation.

2. Your test set: size, coverage, and sealing

  • Size. You have 26 questions. That is a good start for a case study and a small number for a conclusion (next section).
  • Coverage. Your answer key already mixes the useful kinds: easy lookups, a version question, a conflict, a node-boundary question, and unanswerable questions. Keep a count per kind. An average hides a kind that is always wrong.
  • Development set and held-out set. Questions you look at while tuning are the development set. The 10 unseen questions (Teammate A) are your held-out set. Do not look at the results on them while you tune. Use them once, at the end of a phase, to see whether the improvements are real or only fitted to the 26.
  • Overfitting by hand. If you keep changing the prompt until all 26 pass, you have measured how well you fitted 26 questions, not how good the system is. This happens to everyone.
  • Do not copy test questions into prompts. A few-shot example that is also a test question is a leak.

3. Small test sets are noisy

One question out of 26 is 3.8 percentage points. If you ran the system on a different set of 26 equally hard questions, the score would move by chance alone. A confidence interval is the range of true pass rates that are consistent with what you saw. Here is the 95% interval for a pass rate measured on 26 questions (Wilson interval, computed on 2026-11-05):

Read the last row twice: even a perfect score on 26 questions only tells you the true rate is probably above 87%. Read the 20 of 26 row: the interval is 31 points wide. Two systems at 18 and 23 out of 26 have intervals that overlap, so on their own they do not clearly differ.

Comparing two systems on the same questions

Both systems answered the same 26 questions, so use that. Ignore every question both got right or both got wrong. Only the questions where they differ carry information. Count "A right, B wrong" and "B right, A wrong". Then ask: if the systems were really equal, how likely is a split this uneven? (This is the sign test; it is the exact version of McNemar's test.)

So on 26 questions, a new prompt that fixes 4 questions and breaks 1 is not evidence of an improvement. This one table will save you from many false wins. The "5%" line is a convention, not a law: the honest summary is the numbers themselves.

import math

def wilson(k, n, z=1.96):
    """95% interval for a pass rate k/n. Behaves well for small n."""
    p = k / n
    d = 1 + z * z / n
    centre = (p + z * z / (2 * n)) / d
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return centre - half, centre + half

def sign_test(a_only, b_only):
    """Two-sided exact p-value for 'the two systems are equally good'."""
    n, k = a_only + b_only, max(a_only, b_only)
    tail = sum(math.comb(n, i) for i in range(k, n + 1)) / 2 ** n
    return min(1.0, 2 * tail)

Other sources of noise

  • Sampling. With temperature above 0, the same question gives different answers. Run each question several times and report the average, or fix temperature to 0 and a seed. Even then, GPU runs may not be bit-for-bit identical, so repeat a run once to measure how much it moves.
  • Prompt wording. A tiny change (a space, the order of examples) can move a small model's score. Test two or three paraphrases for any prompt you depend on.
  • The judge. A judge adds its own noise on top (next section).

4. Judge models (AI as a judge)

A judge is a language model that reads an answer and scores it with a rubric. It is cheap and scalable, and it is also wrong in ways that are systematic.

Known biases

The MT-Bench paper describes these for strong models; small models are usually worse, but measure it, do not assume it.

BiasWhat happensHow to test or reduce it
PositionWhen comparing two answers, the judge prefers the first (or the second).Swap the order and judge twice. Count how often the verdict flips.
Length (verbosity)Longer answers score higher even when they say nothing more.Check the correlation between answer length and score. Add "length does not matter" and re-test.
Self-preferenceA model rates its own style higher.Use a different model family as judge than the one that wrote the answer.
Weak at facts and arithmeticMisses a wrong number in a fluent answer.Give the judge the key facts as a reference, and check numbers with code.

Making a judge more reliable

  • Judge with a reference. Give the key facts from your answer key. "Does the answer contain these facts?" is easier and more reliable than "is this a good answer?".
  • Prefer small scales. A common practice is yes/no or a 3-point scale for each criterion, and several separate criteria, instead of one 1-to-20 number. A small model cannot tell a 17 from an 18 consistently. Test this on your own judge: run it twice on the same answers and see how often the score changes.
  • Force structure. Ask for the reasoning, then the score, in a fixed JSON shape. Parse it in code and count the parse failures.
  • Calibrate against humans. Label 30 to 50 outputs yourself, without seeing the judge's score. Compare. Report how often they agree, and look at the cases where they disagree.

Agreement in words

If 90% of answers are good, a judge that always says "good" agrees with you 90% of the time and is useless. Cohen's kappa corrects for this: it measures agreement beyond what chance would give. Zero means no better than chance; one means perfect. Always report agreement per category too: a judge can be good on easy lookups and bad on conflicts.

Careful: your 18 out of 20 threshold It is the proposal's default and a decision for your supervisor, so I am not changing it. What you can do is gather evidence for the conversation: (1) the distribution of the judge's scores on a set of answers you labelled good and bad, (2) how often the same answer gets a different score on a second run, (3) how many good answers fall below 18 and how many bad answers reach it. If the scores cluster at 17, 18 and 19, the threshold is cutting through noise.

5. Error analysis: the highest-return hour

  1. Collect 30 to 50 failures (wrong or refused answers). Save the question, retrieved chunk ids, prompt, and answer.
  2. Read each one. Write one line: what went wrong, in your own words. Do not use a fixed list yet.
  3. Group the lines into categories (for example "right chunk not retrieved", "old version used", "number copied wrong", "should have refused", "citation does not support claim").
  4. Count. Fix the largest category first.
  5. Re-run, and write down how that category changed. New categories may appear; that is normal.
Senior habit The failure table is the most valuable document in an AI project. It tells you what to build next, and it is the thing a supervisor or a hiring manager remembers.

6. A regression suite you run on every change

  • Fast checks on every change: unit tests, the 6 validators, deterministic retrieval metrics. Seconds.
  • Slow checks on demand: full model runs and judge runs. Minutes to hours. Save each with a run id, the model tags, the prompt versions, and the chunk policy. (Your baseline_runner already does most of this.)
  • A saved baseline file to compare against. A change that lowers a number by more than its interval should block the merge, or at least trigger a look.
  • Pin the unanswerable questions as their own test group. A system that improves on answerable questions by always answering will quietly break these.

7. Setting targets without inventing numbers

Your metrics have no targets yet, and the right rule is "no target without a source". A defensible way to get one:

  1. Measure the baseline with its interval (Phase 2 data plus the unseen questions).
  2. Decide with your supervisor what an error costs. Is a wrong answer worse than a refusal? A target follows from that, not from a round number.
  3. State the target as a range you can defend, with the interval and the sample size beside it, and record where it came from (your target_source column).
