Small local models

Your system must run offline on a laptop with a 4 GB graphics card. That is a hard constraint, and it makes you learn what most engineers skip: what a model costs. Book chapters 2 and 9.

2. Memory math, in words

Weights

A model is a very large list of numbers (parameters). Each number takes some bytes. So:

memory for weights is about (number of parameters) × (bytes per parameter)

FormatBytes per parameterA 4-billion modelA 0.6-billion model
16-bit2about 8 GBabout 1.2 GB
8-bit1about 4 GBabout 0.6 GB
4-bitabout 0.5 (a bit more in practice)about 2 GBabout 0.3 GB

These are estimates of the weights only. Real files are a little larger because the compressed formats store extra numbers to undo the compression.

Quantization

Quantization stores each parameter with fewer bits. It makes the model smaller and usually faster, at some loss in quality. The loss differs from model to model and from task to task, so measure it on your questions. File names like Q4_K_M or Q8_0 tell you the method and bit count; your glm-ocr:q8_0 is 8-bit.

The context cache (the part people forget)

While the model reads your prompt it keeps, for every token and every layer, two small lists (a key and a value) so that it does not recompute them. This is the KV cache. It grows in a straight line with the number of tokens, and it sits in the same memory as the weights.

cache size is about 2 × layers × KV heads × head size × bytes × tokens

An example with an invented shape (32 layers, 8 KV heads, head size 128, 16-bit): that is 2 × 32 × 8 × 128 × 2 = 131,072 bytes per token, about 128 KB. At 8,000 tokens it is about 1 GB. That alone would be a third of your free GPU memory. Real models have different shapes (look in the model's config file on its Hugging Face page), but the lesson is general: a longer prompt costs memory, not only time.

Senior habit Before you download a model, estimate: weights + cache at your chosen context length + some overhead. If it is near your limit, expect trouble. Write the estimate down, then compare it with the real number from ollama ps and nvidia-smi. Over time your estimates become accurate.

3. Speed: two different costs

  • Prompt processing (reading your prompt). Fast per token, but it grows with prompt length. A long RAG prompt makes every question slow before the first word appears.
  • Generation (writing the answer). One token at a time. Limited mostly by how fast the memory can be read, which is why a smaller or more compressed model writes faster.
  • Partial offload. If part of the model is on the CPU, every token waits for the slow part. Speed can drop a lot. Check the processor split that ollama ps shows.
  • Model swapping. If two models do not fit together, the server unloads one to load the other. Each swap costs seconds. This matters for a pipeline that alternates between embedding and answering.

Compute tokens per second for prompt and for generation, and add them to every run record. Then run the same question at three prompt lengths and plot time against length.

4. Design the pipeline around the memory limit

Not all models are needed at the same moment. Plan two profiles:

ProfileModels neededTip
Ingestion (rare, batch)The vision model for scans; the embedding model to index.Run all the scans first, then unload the vision model, then embed. Speed matters less here.
Question answering (interactive)The embedding model for the query, then the language model for the answer.The embedding model is small, so both can stay loaded. Keep the context short.
Judging and tuning (offline batch)The language model, and a judge model.Run all generations, then all judgements. Do not alternate per item.

Ollama can keep a model loaded for a set time (keep_alive) or unload it at once. Read how it works in the docs and decide per profile.

5. Getting reliable output from small models

A small model follows instructions less reliably than a large one. You cannot fix that with a bigger model, so you design around it:

  • One job per call. "Find the facts" and then "write the answer" beats one big instruction.
  • Short, direct prompts with the task first and a clear output shape. Test whether examples help; sometimes they confuse small models.
  • Constrained output. Ollama can limit output to a JSON schema in recent versions (check the structured outputs section of the docs for your version). That removes a whole class of parse errors.
  • Validate in code, retry once, and count. Report how often a retry was needed. That number is a quality metric.
  • Use code instead of the model wherever a rule is exact: sorting, counting, comparing dates, checking a citation exists.
  • Low temperature for facts. Higher only if you want variety.
  • Thinking models. Some models write a long hidden reasoning first. That costs time and context and can break strict formats. You already excluded the thinking-only qwen3:4b tag for good reasons; keep that note in the registry.

6. Choosing and comparing models

  1. Write the task first (embed in this language, answer from context, read a scanned page).
  2. Filter by fit (the memory estimate) and licence (read it; some licences restrict use).
  3. Pick two or three candidates. More is rarely useful.
  4. Run the same evaluation on all, report intervals (see Evals), and record speed and memory.
  5. Pick the simplest one that is good enough. Record why, with the numbers, in the registry.
Careful A model that scores well on a public leaderboard may fail on your documents, your language, or your prompt format. Use leaderboards to choose candidates and your own test to choose the winner. Also remember the book is a snapshot: model names in it will be old by now.

7. Making an offline system trustworthy

  • Pin versions. Record the Ollama version and each model's digest (ollama show and ollama list display identifying details). A model tag can point to a different file later.
  • Prove it works offline. Your planned run with Wi-Fi off is the right test. Run the full pipeline end to end and confirm nothing fails or waits for a network call.
  • Keep the files. Store the model files and installers somewhere safe, so the system can be rebuilt without the internet.
  • No hidden network use. Check each library for telemetry or automatic downloads, and set them off. A first run that downloads a tokenizer is a classic surprise.
  • Record the hardware with every result: GPU, free memory at the start, driver version. A result from a different machine is not comparable.
  • Plan for failure. What does the system do if the model server is down, if memory runs out mid-run, or if a file is corrupt? Decide now and test it.

Fill it for your three models. This is your finished "how to use the models" evidence and it is the data Phase 14 will need.

8. Fine-tuning: not yet

Fine-tuning means training a model a little more on your own examples. The usual order is: better prompts, then better retrieval and data, then (only if still needed) fine-tuning. It needs data, compute, and an evaluation to prove it helped, and with 4 GB of memory it is limited. Read book chapter 7 when you reach that question, and ask first whether the problem is really in the model.
