RAG in depth

RAG looks simple in a diagram and fails in many quiet ways. This page lists the ways, how to catch each one, and what to try. Book chapter 6, plus chapter 8 for duplicates.

1. The pipeline, and where each stage breaks

Most teams tune the prompt because it is the easy knob. The failure is usually earlier. Check the stages in order.

StageHow it failsHow you catch it
1. Extract textA table becomes a pile of numbers. A scan has no text. Headers and footers repeat in every chunk.Read the extracted text of 5 files by eye. Compare with the original.
2. ChunkThe answer is cut in half. A number is separated from its label. A chunk has no clue which document it came from.For each key fact, check that one chunk contains the fact and enough context to understand it.
3. Embed and indexWrong model for the language. Query and document treated the same when the model expects different prefixes. Old index after a document changed.Search for a sentence copied from a chunk. It must come back first.
4. RetrieveThe right chunk is not in the top k. Exact names, codes and numbers are missed. Chunks from the wrong node are returned.Recall at k on a labelled set (section 2).
5. Assemble contextToo much text. Duplicates fill the space. The key chunk is in the middle of a long prompt.Print the exact final prompt for 10 questions and read it.
6. GenerateThe model ignores the context, mixes in its own memory, or answers when it should refuse.Compare the answer with the retrieved text. Test unanswerable questions.
7. CiteThe citation points to a chunk that does not support the claim.Check that each cited chunk contains the claimed fact (section 9).
Senior habit When an answer is wrong, the first question is always "was the right chunk in the retrieved set?" If no, it is a retrieval problem and a better prompt will not help. If yes, it is a context or generation problem. This one question halves your debugging time.

2. Measure retrieval on its own

Evaluate retrieval without the language model. It is faster, cheaper, and it has no randomness. You need, for each question, the list of chunks that contain the answer (the "relevant" chunks).

MetricIn wordsUse it when
Hit rate at kDid at least one relevant chunk appear in the top k? Yes or no, averaged.One chunk is enough to answer.
Recall at kOf all the relevant chunks, what share appears in the top k?The answer needs several chunks.
Precision at kOf the k chunks returned, what share is relevant? Low precision means noise in the prompt.The prompt budget is small (your case).
MRRLook at where the first relevant chunk is. Rank 1 scores 1, rank 2 scores 1/2, rank 4 scores 1/4. Average over questions.You care about the first good result, for example with a reranker.
nDCGRewards putting relevant chunks higher in the list, and can handle "very relevant" versus "slightly relevant".You have graded relevance labels. Skip it until you do.
def recall_at_k(retrieved, relevant, k):
    """Share of the relevant chunks that appear in the first k results."""
    if not relevant:
        return None   # unanswerable question: nothing to retrieve, score it separately
    return len(set(retrieved[:k]) & set(relevant)) / len(relevant)

def reciprocal_rank(retrieved, relevant):
    for rank, chunk_id in enumerate(retrieved, start=1):
        if chunk_id in relevant:
            return 1 / rank
    return 0.0

Then your E3 comparison is not "which one feels better" but "recall at 3 changed from X to Y, on 26 questions, with this error bar". Keep the table in metrics/ or results/, never inside a case-study document (rule 4 of CLAUDE.md).
Careful Label the relevant chunks before you look at what the retriever returns. If you label after, you will unconsciously mark whatever it returned as relevant.

3. Chunking

A chunk is the unit that is embedded, retrieved, cited and put into the prompt. One size has to serve all four jobs, which is why chunking is a compromise.

ChoiceSmall chunksLarge chunks
Retrieval precisionHigher: a chunk is about one thing.Lower: a chunk mixes topics, so its embedding is a blur.
Context for the modelLower: may miss the label or the date.Higher.
Prompt budgetCheap per chunk.Expensive. Few fit in a small context.
CitationExact.Vague.

Common strategies (try them as experiments, in this order)

  1. Fixed window with overlap (your words80). Simple, predictable, ignores structure. Overlap is insurance against cutting a fact in half; it costs storage and creates near-duplicate hits.
  2. Structure-aware (your sections80). Split at headings and pages. Keeps a section's meaning together. Needs good extraction of headings, which is why DOCX and PDF matter.
  3. Add context to every chunk. Prepend the document title and heading path to the text that is embedded. Cheap and often helpful. Anthropic's "Contextual Retrieval" post describes a more advanced version that uses a model to write the context.
  4. Small to retrieve, larger to read. Search over small chunks, then give the model the whole section they came from. Your heading-path metadata makes this possible.
  5. Semantic chunking (split where the meaning changes, using embeddings). More complex and slower. Try only if the earlier ones plateau.
Senior habit Chunking is a hyperparameter of the whole system. Never judge it by eye. Change it, rebuild the index, and re-run the same retrieval table. Keep the old index so you can compare.

4. Embeddings, in words

An embedding model turns a text into a list of numbers, a point in space. Texts with similar meaning land near each other. Cosine similarity measures how much two arrows point the same direction, and it ignores their length. Search means "find the stored points nearest to the question's point".

  • Query and document are different. Some embedding models expect a special prefix or instruction on the query. Read the model card. Forgetting this silently lowers quality.
  • Language and domain matter. A leaderboard score is an average over many tasks. Your documents are not that average.
  • Dimension and size. More dimensions cost more storage and search time. With 20 documents and a few hundred chunks, the cost is irrelevant today; it matters when the system grows.
  • Changing the embedding model means re-embedding everything. Store the model name and version with the index, so you know which vectors belong to which model. This is why your model registry exists.
Go check this yourself
  • MTEB leaderboard: a broad comparison of embedding models. Use it to pick candidates, then test them on your own questions. Look at the retrieval tab and the model sizes.
  • BEIR: the reason people test on their own data (a method strong on one dataset can be weak on another).

5. Hybrid search: keywords plus vectors

Vector search is good at meaning ("fleet size" matches "number of buses") and weak at exact strings ("Route 12", "D10", a part number). Keyword search (BM25) is the opposite. Using both and merging the results is a standard fix.

  • BM25 scores a chunk by how many of the query's rare words it contains, with a limit on very long chunks. It is classic and fast.
  • Reciprocal rank fusion (RRF) merges two ranked lists using only the ranks, not the raw scores (which are on different scales). Each list gives a chunk the score 1 divided by (k plus its rank), and the scores add up. A common value for k is 60.
  • You already have SQLite. Its FTS5 module provides full-text search and a bm25() function, so keyword search needs no new service. That fits an offline system very well.
def rrf(rankings, k=60):
    """Merge ranked lists of chunk ids. rankings = [vector_ids, keyword_ids]."""
    scores = {}
    for ranking in rankings:
        for rank, chunk_id in enumerate(ranking, start=1):
            scores[chunk_id] = scores.get(chunk_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

I tested your virtual environment on 2026-11-05: it has SQLite 3.53.1 and FTS5 works, including bm25(). So keyword search can live in the same SQLite file as the rest of your data.

6. Reranking

The first search is fast and rough: it compares pre-computed points. A reranker (often a "cross-encoder") reads the question and one chunk together and scores how well the chunk answers the question. It is more accurate and much slower, so you apply it only to the top 20 to 50 results and keep the best few.

  • Cost: one model run per candidate chunk. On a 4 GB GPU, check the memory with the embedding and language models loaded as well.
  • Gain: unknown until you measure. Use the same retrieval table (MRR and recall at 3) with and without it.
  • A small language model can act as a reranker with a prompt, but it is usually slower and less stable than a model trained for the job.

7. Retrieval limited by the hierarchy

Your system answers "limited to one node". This is a strength: it removes a whole class of wrong answers. Do it correctly:

  • Filter before you rank (pre-filter). If you rank first and filter after, you may discard all the top results and be left with nothing.
  • Put the scope in the chunk metadata (node id, active version) and make the filter part of the repository, not of the prompt. A prompt that says "only use node N4" is a hope; a filter is a guarantee.
  • Measure leakage. Count how many retrieved chunks are outside the asking node's scope. It must be zero. A test that proves it is worth more than a paragraph explaining it.
  • The other side of the trade-off: a strict filter can hide a useful document in a neighbouring node. Your Q22 (the node-boundary question) is exactly this test.

Senior habit Deduplication is a decision about what the system should believe, not only a cleaning step. Log every merge and every skip with the reason, so a person can undo it.

9. Context assembly, citations and refusing to answer

  • Budget. Decide the maximum context in tokens. Small models degrade with long prompts (see Local models). Fewer, better chunks beat many mediocre ones.
  • Order. Models tend to use the start and end of a long context better than the middle (the "Lost in the Middle" paper). Put the strongest chunks first.
  • Remove repeats. With overlapping chunks, the same sentence may appear twice. Merge neighbouring chunks.
  • Label every chunk with its citation id in the prompt, and ask the model to cite only those ids.
  • Check the citations in code. A cited id must exist in the retrieved set. Better: the cited chunk must contain the key numbers or names in the answer. This is cheap, deterministic, and catches many hallucinated citations.
  • Refusing. Tell the model it may answer "not found in the documents". Then test it on the unanswerable questions in your answer key. A retrieval-score threshold ("if the best score is below X, refuse") can help but is fragile; measure it before you trust it.
Go check this yourself Lost in the Middle and the Ragas documentation (a library of RAG metrics such as faithfulness and context precision). Read the Ragas metric definitions to learn the vocabulary. Note that many of its metrics use a language model as the judge, so the cautions on the Evals page apply.

10. A debugging checklist

  1. Print the question, the retrieved chunk ids with scores, and the final prompt.
  2. Is the key fact in any chunk at all? If not, go to extraction or chunking.
  3. Is that chunk in the top k? If not, retrieval: try keywords, a different k, a different chunk size.
  4. Is it in the prompt, and not buried or cut off by the context limit?
  5. Does the model's answer match the chunk? If not, generation: simplify the prompt, lower the temperature, try another model.
  6. Is the citation correct?
  7. Write the failure into a table with a category. After 20 failures, fix the biggest category.
