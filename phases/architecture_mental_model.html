1. The Core Mental Model: Domain-Driven Design (DDD)

When you build an AI system or RAG application, the biggest rookie mistake is mixing up your business logic (what a chunk is, what a knowledge version represents, how organizational hierarchies operate) with your technical infrastructure (SQLite SQL statements, Ollama REST API calls, pypdf binary reading).

In our project, we use Domain-Driven Design (DDD). The system is split into two strict worlds:

  • The Inner Domain (rag_core/knowledge/, rag_core/organization/): Pure Python logic. It knows nothing about SQLite, filesystems, HTTP, or Ollama. It only knows business rules (aggregates, value objects, domain invariants).
  • The Outer Infrastructure (rag_core/infrastructure/, rag_core/ingestion/): Adapters that plug into the domain. They talk to SQLite, read PDF bytes, call Ollama, and write CSV files.
Why this matters: If you wanted to swap SQLite for PostgreSQL tomorrow, or Ollama for Llama.cpp, you would write a new adapter in infrastructure/ without changing a single line of business logic in the domain core.

2. How Components Talk to Each Other (Ports & Adapters)

Components communicate via strict boundaries. They never reach across layers arbitrarily. Here is how data and commands flow through the system:

[ CLI Command / User ] │ ▼ [ Application Services ] (e.g., IngestionService, OrganizationService) │ ├─────────────────────────┐ ▼ ▼ [ Domain Aggregates ] [ Infrastructure Ports / Adapters ] (Guards rules & state) (Reads PDFs, calls Ollama, talks to SQLite) │ │ └─────────────────────────┘ │ ▼ [ Persistence Layer ] (SQLite & CSV Exports)

Step-by-Step Interaction Example (Ingestion):

  1. CLI / Entrypoint (`rag_core/__main__.py`) receives a command like python -m rag_core ingest-case-study.
  2. Application Service (`IngestionService`) coordinates the run. It asks the hierarchy repository for node rules, and asks extractors for raw text.
  3. Extractors (`rag_core/ingestion/extractors.py`) read the raw file bytes (DOCX, PDF, MD) or invoke the LVM vision adapter if it's a scanned PDF.
  4. Domain Model (`KnowledgeItem`, `KnowledgeVersion`, `KnowledgeChunk`) receives the raw data, applies chunking policies (words80), computes SHA-256 fingerprints, and checks lifecycle states.
  5. Infrastructure Repositories (`SqliteKnowledgeRepository`) persist the resulting records into SQLite and export mirror CSVs (`catalog.csv`, `chunks.csv`).

3. How We Are Using the Database Thingy (Persistence Strategy)

You might wonder: Why do we even need SQLite and CSV databases? Why not keep everything in memory?

A. Why SQLite?

  • ACID Guarantees & Relational Integrity: When we ingest 20 documents and 100+ chunks across 7 nodes, we need relational constraints. A chunk belongs strictly to a knowledge version; a version belongs to an item; an item belongs to a node. SQLite enforces foreign keys and guarantees data isn't half-saved if an error occurs.
  • Stateful Queries: When Phase 8 retrieval runs, it needs to query: "Give me all active chunks belonging specifically to Node N2." SQLite executes this query instantly using indexed lookups.
  • Audit Trail: Version 1 and Version 2 of document D10 both need to be stored for history, but only v2 is active. SQLite handles versioned rows effortlessly.

B. Why Duplicate CSV Mirroring?

Every time SQLite writes data, our infrastructure code (`rag_core/infrastructure/csv_export.py`) simultaneously writes human-readable CSV snapshots (`catalog.csv`, `chunks.csv`, `duplicates.csv`, `ingestion_report.csv`). This gives you the best of both worlds: fast relational queries via SQLite, and instant human inspection via CSV files.
