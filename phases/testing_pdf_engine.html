1. Tests & Validators: What, Why, and How

To ensure absolute correctness, our project relies on two distinct layers of automated checks: Consistency Validators and Unit Tests.

A. The 6 Consistency Validators (`tools/run_checks.py`)

  • What they do: They inspect your project data files (`case_study/`, `registry/`, `scope/`, `glossary/`, `metrics/`, and documentation markdown reports) and cross-check them against strict relational rules.
  • Why they exist: In complex academic projects, human errors happen. For example, if you update the case study manifest to add 21 files instead of 20, or if a markdown table disagrees with the metrics CSV, human reviewers would miss it. The validators act as an automated tripwire.
  • How they are defined: Written in pure Python in tools/run_checks.py. They parse CSV columns, check file existence on disk, verify text hygiene (UTF-8, LF line endings, no accidental Persian text in English files), and ensure that every metric and hard rule is mapped to a test area.

B. The 328 Unit Tests (`pytest tests/`)

  • What they do: Test individual domain components, workflows, chunking rules, duplicate detectors, and citation formatters in isolation.
  • Why they exist: Domain-Driven Design (DDD) requires that domain rules are infallible. Unit tests prove that aggregates enforce their invariants (e.g., verifying that an exact duplicate is skipped, that moving a node under itself throws a domain error, or that chunk text matches the Phase 2 baseline exactly).

2. Where Are the Results? (Execution Output Artifacts)

When you run system commands like case study ingestion or duplicate scanning, where do the results go and what do they contain?

  • Ingestion Runs (`results/ingestion//`): Every time you run ingestion (e.g., python -m rag_core ingest-case-study --run-id phase4-words80), a dedicated folder is created containing:
    • knowledge.sqlite — The relational database holding all items, versions, chunks, and metadata records.
    • catalog.csv — A flat spreadsheet listing every registered knowledge version, its node, file hash, and active status.
    • chunks.csv — Every individual text chunk, its source location, and page range.
    • ingestion_report.csv — Detailed breakdown of every processed file (success, warning, chunk count).
    • duplicates.csv — Advisory logs of exact, near, and overlap duplicate findings (when --detect-duplicates is enabled).

3. Handling PDFs: Why Use `glm-ocr` (LVM) When We Have `pypdf`?

A very common and critical question during evaluation is: "Why do you need a Vision Language Model like `glm-ocr` to read PDFs when standard Python libraries like `pypdf` already exist?"

The Short Answer:

`pypdf` reads text layers; `glm-ocr` reads images of pages. If a PDF is a scanned document (like archived city council meeting minutes D19), it contains zero digital text—it is literally just a picture of paper saved inside a PDF container. To `pypdf`, a scanned PDF appears as a completely empty blank page.

How Our Hybrid PDF Pipeline Works (`rag_core/ingestion/extractors.py`):

  1. Text Extraction Attempt: When a PDF is ingested, our extractor first uses `pypdf` to extract the digital text layer.
  2. Density Check: It calculates the average word count per page.
  3. The Fallback Trigger: If a page has fewer than 5 words on average, the system detects that it is a **scanned page**.
  4. Rasterization & LVM Vision Reading:
    • `rag_core/ingestion/png.py` renders that PDF page into a high-resolution PNG image.
    • The image is sent to our local Vision Language Model (`glm-ocr` running on Ollama).
    • The LVM "looks" at the image of the scanned page, performs optical character recognition (OCR) and layout understanding, and returns the transcribed text.
Why this is brilliant: It gives your RAG system the superpower to ingest both modern digital documents and messy historical scanned paperwork without human pre-processing.
